# Successor scan and signed admission hardening

The public incremental semantic scanner now rebuilds facts whose resolved graph context can change, while retaining the source-local fast path. Signed inventory and successor admission now reject late receipt changes and reserve declared creations before signing. These repairs strengthen the inputs to repository planning; they do not complete the live preview to signed worker bridge. All 32 production acceptance rows remain open.

## Incremental scan equivalence

An unchanged caller previously retained resolved edges when a dependency disappeared or changed. Reusing an already resolved ambiguous edge could also upgrade `finite_may` to `definite`. The scanner now computes one operation-local set of paths requiring analysis, covering cross-file edges, resolver metadata, derived Protocol edges, pytest records and changed raw edge extractor versions. It checks the actual namespace and symbol extractor identity before skipping analysis. After analysis, it retains a prior symbol object only when the complete immutable record equals the fresh result.

Protocol inheritance now accepts tuple bases produced by immutable record normalization. Failed Python analysis always runs again: its opaque diagnostic artifact has no analyzer identity with which to establish compatibility. Successful, unambiguous source-local paths still skip parsing. No durable schema, persistent freshness token or numerical inference behavior changes.

The 21 new scanner cases compare complete cold and incremental state bytes, roots, deltas and invalidation obligations. They cover ambiguous targets, removed and renamed dependencies beyond the first 32-member slice, Protocol changes, pytest scope, record identity, namespaces, extractor changes and opaque diagnostics. The full scanner regression suite passed 87 cases.

The equivalence claim assumes prior states genuinely produced by the compatible frontend. Direct source-local reuse still trusts prior fact population and auxiliary fields; these controls do not authenticate arbitrary constructor-valid cache records. Formalizations remain proposals until a checker verifies them against the current source snapshot.

## Signed admission custody and source capacity

Both private admission operations pin detached admission and returned receipt bytes, require exactly one successful close, and repeat their wire checks after the operation body and resource exit. Success is withheld if a callback or closing scope leaves the captured signed task population or receipt bytes changed at a closing check. These sequential observations do not detect a transient mutation restored before observation. Success-only checks preserve body and current-owner-close exceptions.

Manifest authoring now validates declarations before signing. The source cap includes every unique declared creation: 1,024 existing sources plus one new path refuses, while 1,023 plus one and 992 plus 32 fit. The existing 128, 256 and 1,024 profile caps and complete task populations remain intact. The repair avoids an inevitable refusal when the postcreation inventory exceeds the same cap used during admission.

The 28 new closure cases and 32 new capacity cases passed in the 127-case integrated admission suite. A separate 131-case worker execution, reservation and constructor cleanup suite also passed. Protocol tests identify their owner fence doubles; these runs do not substitute for fresh native worker qualification.

## Validation and retained evidence

The three current suites contain 345 distinct passing JUnit cases, including 81 new cases, with zero failures, errors or skips. Each ran under the unchanged shared resource configuration. Source pins stayed stable and each owned lease closed. Required pytest AST sealing remained enabled; the admission and worker runs used fresh owned seal databases so earlier pass records did not suppress execution.

The corrected prechange capacity run has ten expected gap failures and no fixture errors. The scanner baseline has eight cold versus incremental mismatches plus one cold Protocol prerequisite failure. Earlier fixture errors, the intermediate 85-case scanner run and an admission run with 95 passes and 32 seal-cache skips remain historical evidence and contribute nothing to the current positive count. The admission source capture explicitly records that its two closure modules were already repaired when copied.

The final scheduler observation has zero active leases, allocations or waiters. The authorized Leanstral service remains inactive with MainPID zero; the GPU compute process query was empty. No fresh CUDA or encoder run was needed for these scan and admission changes. Existing 8D, 384D, 768D and 4096D inference evidence retains its original scope and pins.

## Next integration milestones

The [followup plan](../architecture/repository_proof_index_and_codebase_ir.successor_hardening_followup_plan.json) preserves these gates:

1. Add an explicit versioned bridge from the full preview material snapshot and live `PlanAuthorityRoots` to signed successor admission. Bind every requirement and task, and recheck source, model, checker and policy roots at entry and close.
2. Compare complete cold, resumed, optimized and opt-out scans across every inventory page, including dependency invalidation across page boundaries. Join the semantic state and required reproof obligations to the signed worker evidence.
3. Qualify a fresh complete native signed worker run under that bridge, with late mutation, cancellation, cleanup and full population controls.
4. Obtain authenticated native encoder outputs and trained per-width lineages for 768D and 4096D. The retained 768D head has one historical optimizer step; the retained 4096D evidence is synthetic and does not qualify trained Leanstral inference.
5. Integrate federated rounds that produce one accepted model per lineage, with DuckDB or DuckLake transactional metadata and binary tensor artifacts. Preserve an explicit interface for later gradient synchronization through `ipfs_accelerate_py` and MCP++.
