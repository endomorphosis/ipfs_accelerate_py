# Full 300 sequential numerical chunks

The fresh CPU fixture encoded all 294 eligible members of its 300-entry inventory in both default and reference modes. Each mode used 14 sequential numerical requests within the unchanged 32 MiB input cap, produced exactly equal per-source projections, continued in a separate fresh process and passed current completion receiving. The current source generation matched its retained implementation copies at final close. The new chunked route defaults to optimization enabled and retains an explicit opt-out.

The new chunked route addresses the numerical coverage gap in the [previous full300 qualification](codebase_full300_companion_and_linear_observation_qualification_v3.md). That campaign retained all 300 inventory entries but encoded only 110 rows per mode, with 184 eligible rows deferred by the 32 MiB request limit. The new coordinator fills and drains one numerical request at a time, then retries the same member in an empty request. It preserves the existing worker protocol and its request limits.

This fixture uses 53 structural input features and an 8-wide latent. Its 294 eligible rows are distinct from a trained semantic 8D source head. The 384D, 768D and 4096D source/head integration gates remain recorded in the [four-head integration note](codebase_larger_head_native_owner_integration_note.md). This campaign does not establish a full working-repository scan, CUDA execution, formal proofs or trained larger-head CodebaseIR dispatch.

The campaign took 2,589.62 seconds including setup, verification and container cleanup. The seven retained scan/continuation/completion/receiving phases total 927.49 seconds for default and 1,496.82 seconds for reference, about 38% lower recorded phase time on this single equal-work fixture. Numerical child receipts total 279.305 and 426.713 seconds respectively, including their startup, validation, inference and cleanup. These observations do not establish a general throughput result; `throughput_qualified` remains false. Both modes use the default index observation optimization, so the scan switch does not isolate its contribution.

Each mode transferred about 431.94 MB of canonical request bytes. The largest actual request was 32,313,398 bytes, below 33,554,432. Default workers recorded 294 native target replays and 14 state/contract validations, compared with 588 replays and 28 state/contract validations in reference. Both modes built 14 matrices, 14 vocabularies, 56 weight tensors and performed zero training calls. Saved per-source numerical values are exactly equal.

The [coordinator](../../../ipfs_datasets/ipfs_datasets_py/logic/software_contracts/codebase_inventory_chunk_scan.py) exposes `start_current_codebase_chunked_scan`, `scan_current_codebase_page_chunked`, `complete_current_codebase_chunked_scan` and explicit current page/completion receiving. A new root defaults to `optimized=True`; exact boolean `False` selects the reference path. The older single-request scan API and its version 1 records remain available. The chunked route has not been installed as the global production dispatcher or added to signed worker contexts.

Both chunk modes use the unchanged `codebase_inventory_resume_worker@1` request: full canonical targets and model state, CPU float64 inference, at most 32 MiB input, 4 MiB per target and 16 MiB output, with one CPU and 1 GiB sampled RSS per child. Only one numerical child runs at a time. A genuinely oversized singleton retains an explicit byte-budget disposition; global row, native-byte and feature frontiers remain enforced. The aggregate campaign deadline does not raise any per-request byte or resource limit.

The [new records](../../../ipfs_datasets/ipfs_datasets_py/logic/software_contracts/codebase_inventory_chunks.py) use numerical chunk version 1, page/cursor/completion version 2 and the `chunked-native-projection-feature-inference@1` profile. Every chunk retains ordered membership indices, canonical target and source digests, finite projections, actual worker counters and receipt, and the process lifecycle observation. Page and completion records conserve all inventory dispositions, numerical rows and projection records. Each raw CIDv1 chunk/page/completion is bounded by 16 MiB; the existing structured root remains bounded by 4 MiB.

Current receiving reconstructs the source and target joins, checks the complete prefix and model lineage, and closes the source, catalog, SQL and checkpoint observations. It streams one retained chunk at a time. CAS guards run before the independent native close; a final held-FD byte check then detects mutation after that close without invoking extensible CAS callbacks. This is a sequence of fresh observations rather than an atomic filesystem/database snapshot. Receiving and completion run no numerical forward pass or fitting.

The [owned-process interface](../../../ipfs_datasets/ipfs_datasets_py/logic/backends/process.py) is additive and opt-in. Ordinary tool results retain their prior shape. Numerical and fresh-resume launches retain birth-bound native process observations, including sampled descendants that create separate sessions. The coordinator holds its parent and child reservations through confirmed leader reaping, observed descendant/group drain, pipe-thread joins and workspace removal. If cleanup cannot be confirmed, a cleanup owner keeps attempting it while reservations remain held; renewal failures do not acknowledge successful cleanup. These observations are sampled ownership evidence, not kernel containment or independent process-origin attestation.

The selected 279-case control suite includes [18 genuine native chunk scan cases](../../../ipfs_datasets/tests/integration/logic/software_contracts/test_codebase_inventory_chunk_scan.py), [chunk record and conservation controls](../../../ipfs_datasets/tests/integration/logic/software_contracts/test_codebase_inventory_chunks.py), [native lifecycle controls](../../../ipfs_datasets/tests/integration/logic/backends/test_owned_process_observation.py), and existing process/resume compatibility cases. The separate [finite reader](../../../../artifacts/codebase_ir_terminal_bench/verify_full300_chunks_v2_20261006.py) checks selected ordinary evidence using SHA256, raw CIDv1 and canonical structured identities. It checks both five-page chains, all ordered chunk maps, recorded worker counters and limits, default/reference projections, source history and setup records, frozen checkpoint identities, sampled child/launch joins and recorded container cleanup. The [copied controls](../../../../artifacts/codebase_ir_terminal_bench/check_full300_chunks_reader_controls_v2_20261006.py) define 52 refused mutations and one coherently rebased positive when both outer receipts are supplied. The positive changes copied locators and refreshes their joins; it adds no new execution credit. Only one disposable copy is active at a time.

The finite reader imports no producing implementation and replays no inference, training, signing or native database operations. Private model and database artifacts, credentials, external native binaries and the source-delta ledger are excluded from its selected byte closure. Their recorded hashes and native observations are producer claims. The reader does not independently verify those asset bytes, public signatures, process origin or formal proofs. The audit receipt must be read with this scope attached.

The [first chunked campaign](../../../../artifacts/codebase_ir_terminal_bench/full300-chunks-native-20261006-01/container-execution-final.json) passed all native rows, current completion receiving and default/reference equality against its immutable copies, then correctly failed the outer current-generation gate. Those changes and the failed outer receipt are preserved. Fresh roots now also pin the directly used `content.py` module; no historical result is relabeled as current.

The [bounded encoding gap plan](../../../../artifacts/codebase_ir_terminal_bench/full300-encoding-gap-plan-20261005-01/plan.json) remains a sealed historical proposal. This implementation addresses its sequential-chunk milestone. Its shared-manifest transport milestone remains open: the transport repeats the full manifest per target and model state per request. The campaign measures coverage and equivalence, not a general inference throughput improvement. Reducing repeated serialization and manifest decoding requires a new explicit transport profile, receiver checks, process ownership and fresh native qualification.

Shared wire bytes also need a separate decoded-memory bound. The current worker restores and retains every full target before building its input matrix. A smaller shared-manifest request could therefore admit more restored target data than the existing wire cap bounds. A new worker must stream native row replay into bounded feature vectors or enforce an explicit full-target retention ceiling, and measure actual RSS before claiming fewer safe launches per page.

Signed full300 worker dispatch also remains open. The old complete inline parent exceeds the unchanged Intent task-body limit. The [compact artifact contract design](codebase_compact_successor_artifact_contract_design.md) requires immutable bounded artifact references, complete task population, signed current receiving and worker integration with the new chunked completion. Existing signed parent and worker protocols remain strict; an old completion cannot be relabeled as a new chunked completion.

The [verified checkpoint read proposal](codebase_verified_checkpoint_read_proposal.md) and SQL observation batch candidate remain unapplied. The former would share one held-FD read for parsing and comparison while retaining independent closing hashing. The latter needs a compatibility redesign because its aggregate singleton limits are stricter than the old member path. A proposed fallback would close and discard the batch preflight before calling the original per-member lookup when an optimization-only capacity limit is exceeded. Schema, owner, duplicate/missing row and provenance failures remain terminal. New receipt counters, genuine singleton-boundary tests and measured memory after buffer disposal are required before activation. Neither candidate has inference performance credit here. The [Repository Proof Index work](../architecture/repository_proof_index_and_codebase_ir.todo.md) retains production worker publication, shared-model federation, future gradient synchronization, four-head qualification and checker-accepted proof gates.
