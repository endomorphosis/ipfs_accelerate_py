# Signed repository preview and successor companion

A new signed companion joins the complete repository planning input to an independently admitted successor task graph. It binds source and semantic-state identities, live authority roots, checker policy, model lineage and every authored task and acceptance check. It is proposal metadata. Worker construction and START still require a dedicated profile that carries this binding through their own native fences.

## Complete planning and task bindings

The [contract](../../ipfs_accelerate_py/agent_supervisor/runtime/codebase_preview_successor_contract.py) reconstructs the repository preview's structural augmentation and material-bound input snapshot at version 2. It requires supported, complete semantic material identity and a deterministic read-only preview. It recompiles the obligation graph with no observed behavioral facts, then checks a bijection from every authored candidate to every signed task, exact dependency correspondence, and complete predicate-to-task and acceptance coverage. The full signed graph preserves validations, outputs and pending requirements.

Create-plan requests and prompt-workflow requests have different schemas. Structural preview scans and directory scan receipts also have different schemas. Their identities remain separately named in an explicit mapping; equality is not inferred. The semantic program root must agree with the same source owner's immutable manifest. Model metadata, training record and checker-policy identity have separate bindings because `PlanAuthorityRoots` has no dedicated CodebaseIR model or checker field.

The companion has a 2 MiB limit and derives its CIDv1 identity from the complete record. It carries neither raw source nor model weights. Its coverage describes administrative task requirements; it does not establish that a task's checks prove an intent predicate or that the preview portfolio selected every mapped task.

## Current observations and closing order

The [owner wrapper](../../ipfs_accelerate_py/agent_supervisor/runtime/codebase_preview_successor_admission.py) exposes `author_current_preview_successor_bridge` and `verify_current_preview_successor_bridge`. Callers supply the existing signed admission, typed request and preview, original repository-preview materials, explicit mappings, and trusted live root and checker observers. Signature verification uses the existing local profile authority.

Two bounded native successor receiving operations surround the application observations. The first checks the existing admission and joins the same index's immutable manifest to the selected head, snapshot, AST revision and semantic state. After its cleanup, a fresh operation checks application roots, checker policy and complete materials again, then performs the final native source and model close. All application observers, CAS reads, signing and obligation compilation finish before that last native close. Only passive snapshot and detached byte custody checks follow it.

Request and preview records are detached into canonical base records before receiving. The material profile accepts only reviewed exact record types and passive builtin metadata. Material guards reject custom serializers, unknown dataclasses, subclasses, live containers and proxy-backed custom mappings before their hooks execute. Finite builtin metadata numbers remain supported in semantic input digests. PID, thread, cancellation, deadlines and one-use closing gates stay bound throughout the operation.

These are sequential observations, not an atomic lock across source, policy and checker owners. Byte checks detect changes present at their checkpoints, not transient changes restored before observation. No freshness token survives into a later call. A signed companion cannot be supplied as an existing local admission: the legacy parser rejects it.

## Qualification

The final three CPU suites passed 99 distinct cases with zero failures, errors or skips: 90 signed companion and passive-input controls plus nine native structural-reader cases. Genuine Git repositories, profile signatures, deterministic planning stages and full-task replay are used in the companion controls. Their source/model/checker observation callbacks are explicit protocol doubles. The separate reader cases use a real local source index and actual CAS manifests; they do not qualify a full native successor model or worker run.

An initial 80-case run passed before review identified a callback-order gap. A new regression then reproduced a source edit after the native close being incorrectly accepted. The repaired final suites include that regression and reject the edit. Both earlier receipts remain historical and are excluded from the 99-case count.

Each final suite used fresh required pytest seal storage under the unchanged shared CPU resource configuration. Current source pins stayed stable and every owned lease closed. The final observer recorded zero active leases, allocations and waiters. Leanstral remains inactive with MainPID zero, and the GPU compute query was empty. No encoder, CUDA, training or worker execution was added; the existing 8D, 384D, 768D and 4096D qualifications retain their original limits. All 32 production acceptance rows remain unchanged and open.

The [machine review](../architecture/repository_proof_index_and_codebase_ir.preview_successor_bridge_review.json) records exact receipts, sources and followup gates. Its [finite byte closure](../../../../artifacts/codebase_ir_terminal_bench/preview-successor-bridge-review-20261005-01/closure.json) and [independent check](../../../../artifacts/codebase_ir_terminal_bench/preview-successor-bridge-independent-20261005-01/receipt.json) check selected ordinary bytes with SHA-256 and local CIDv1 identities. They do not execute retained producers, publish to IPFS or confer proof authority.
