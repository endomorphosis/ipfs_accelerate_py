# Scoped header proof key custody and restart replay

The scoped header proof workflow can retain a complete native Doctor key and
its canonical preparation beside the actual sealed proof. This closes an input
custody gap in the production recipe. Custody itself does not supply the generic
positive receipt accepted by `DoctorProofCacheGate`. The separate reviewed
[scoped header cache bridge](header_proof_cache_bridge.md) performs that admission
after fresh native kernel replay. Actual Terminal proof coverage remains unmeasured.

## Prepare the current inputs

[`prepare_header_contract_proof`](../../ipfs_accelerate_py/agent_supervisor/runtime/doctor_contract_proof.py)
replays the signed task scope, current source, exact Python AST candidate and
optional SecurityIR bindings before constructing the reviewed theorem and
lowering. It captures actual Lean/Z3 bytes, the Python executable, adapter,
configuration and full role-specific command arguments. It executes no prover
and constructs no proof or metadata owner. Missing local tools return explicit
unavailability through the existing proof wrapper.

Supply `HeaderContractProofKeyProfiles` for corpus, registry, policy, sandbox and
environment. Each is an exact native identity with retained canonical bytes and
a concrete versioned declaration. These are explicit host admissions. They do
not authenticate a declaration, prove corpus coverage or certify isolation.
Diagnostic placeholders and the diagnostic-only policy cannot stand in for
these profiles. The diagnostic snapshot retains its observed source corpus;
the admitted profiles enter the proof theorem and complete key separately.

The complete key binds signed forest/tree/overlay/candidate scope, original AST
and import graph preimages, the exact theorem, reviewed source premise, actual
translator/toolchain and executable pins, explicit profiles, requested bounds
and kernel assurance requirement. Goal identity is the proof obligation, not
the task CID. `HeaderContractProofPreparation.assert_current()` independently
rebuilds those inputs and compares their whole canonical preparation.

The preparation stores detached canonical dictionaries. Altering a returned
report cannot alter retained inputs. Creation and replay run under the existing
metadata-suppression context. Key generation grants no proof, execution,
completion or publication authority.

## Preserve the source premise exactly

The native header contract calls its public static AST observations `witnesses`.
The general public-key classifier conservatively rejects that field name.
The producer uses a separately versioned reviewed source-premise projection
after exact current source replay. It preserves the observations visibly under
an explicit AST-observation field, retains every other contract field and the
original contract CID, and supports an exact inverse.

Only the closed observation shape emitted by the reviewed header AST recipe is
eligible: source identifiers and lines, callback/property/setter relations,
normalizer joins and the fixed partial-scope frontier. Arbitrary witness bodies,
extra fields and private fields refuse. The inverse must recover the original
canonical contract and its CID, with equality to the independently replayed
contract. The projection has its own strict-artifact CID; its logical premise
reference remains the actual original contract CID. The general private-key
classifier is unchanged. The reviewed generic bridge checks this correspondence;
a projected identity cannot stand in for accepted proof.

## Retain the original native owner

`prove_header_contract(..., proof_key_profiles=profiles)` runs the existing
native proof recipe. Successful reports now retain `proof.to_record()`, including
the final sealed authoritative reference needed for restart. With a complete
prepared key and successful native proof, the wrapper seals one bounded
`HeaderContractProofKeyCustody` record in the same SQLite owner. The report
retains the custody reference and full key identity, with
`generic_cache_admission_supported=False`.

The private custody record retains original source/contract preparation, full
profiles and key, actual pins/bounds, and the exact final sealed proof reference.
Keep the existing store and private seal key together under host-controlled
custody. No seal key is exported to a report, model prompt or public artifact.
Historical reports that omitted the final reference cannot be reconstructed
from a proof CID alone; this implementation adds no locator discovery.

## Replay after restart

Rebuild preparation from independently admitted current signed source, profiles
and actual tools. The host supplies an existing native Hammer/store with both
current trusted pins and the exact current requested bounds. Call
`replay_header_proof_key_custody` with the retained typed custody reference and
an independently expected full key identity. The helper constructs no store,
Gate or generic receipt and discovers no database locator.

Replay verifies closed custody schemas, exact canonical preparation, the
original sealed proof and its solver/kernel lineage. It retains strong owner
references and checks canonical paths, device/inode, owner-controlled files,
authority/store identities and original seal-key contents around native
operations. Source, implementation, profile, pin and bounds changes refuse.
It then reruns the actually pinned native kernel before returning its native
proof. A cache miss or a custody record alone cannot authorize that return.

Checks are sequential, not an atomic filesystem lease. Requested CPU, memory
and network limits are retained inputs; this adapter does not certify OS
enforcement. Initial proof creation and custody persistence append records to
the existing owner. Restart replay reloads retained lineage and runs the kernel;
its adapter does not append a new sealed record. This is not a promise that the
invoked executable has no filesystem effects. Record byte bounds do not bound
the native loader's lineage-prefix work; qualify that cost before model access.
