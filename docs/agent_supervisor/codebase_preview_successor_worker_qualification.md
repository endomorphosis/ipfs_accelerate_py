# Preview-bound successor worker profile

The signed repository preview companion now has an explicit worker profile. A child manifest carries its immutable successor admission and signed companion through full task installation, public instruction replay, resource reservation, runtime construction and START receiving gates. Learned matching preserves every independently authored task, validation, output and acceptance requirement. This integration grants neither semantic proof nor production authority; all 32 production acceptance rows remain open.

## Closed signed contracts

The manifest advances to version 7, the planning receipt and its owner-storage reference to version 5, and the pending completion contract to version 3. The child manifest embeds the complete original version 6 admission and signed companion. Its remaining declarations must equal the parent exactly. The companion continues to hash that immutable parent, avoiding a circular identity between the companion and its child.

The receipt, reference and pending contract retain the parent admission CID, signed companion CID, companion body CID and complete child-context CID. Pending contracts also retain the full graph and signed planning receipt for replay. Sources, declared creations, exact dependencies and post-execution gates keep their existing bounds. Existing public inventory and successor profiles reject the child; public instruction version 5 explicitly selects it. Generic materialization rejects the child; runtime launch requires its dedicated active worker scope.

The [pure worker context](../../ipfs_accelerate_py/agent_supervisor/runtime/codebase_preview_successor_worker_context.py) verifies retained signatures, canonical typed request/preview/snapshot records, structural head and semantic-state identities, explicit root mappings and complete administrative task/acceptance populations. Material snapshots contain field digests rather than their original bodies. Public replay therefore does not reconstruct the original producer closure, observe current private owners or execute a checker. The separate current-owner route performs that full material reconstruction.

## Native boundaries and transaction order

The [worker admission route](../../ipfs_accelerate_py/agent_supervisor/runtime/codebase_preview_successor_worker_admission.py) requires exact private preview inputs and trusted live root/checker observers on every use. It consumes the companion's fresh receiving operation, then holds a separate native successor operation across the requested boundary. Application observers, CAS reads, compilation and signature work finish before the final native source/model close. Only passive custody and byte checks follow that close. Gates bind the operation to its process and thread and require one successful closing preparation and close.

Installation prepares the complete signed population without holding the target Intent writer lock. A recorder bounded to 64 operations retains the original materializer's objective, goal, plan and task operations. Application preparation finishes before the write transaction; the transaction rechecks that every task is new, installs the prepared population, then consumes and exits the native receiver before COMMIT. A closing or resource-exit failure rolls back the entire population. The recorder grants no scheduling permission.

Reservation, constructor and START each acquire fresh receiving state. Application preparation precedes the native Quack owner lock; the final native close and detached task/artifact checks precede the boundary's commit or process birth. STOP and cleanup retain their existing resource-custody rules when roots drift or cancellation occurs. These are sequential observations, not an atomic snapshot across all owners or a reusable freshness token.
