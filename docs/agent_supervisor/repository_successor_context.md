# Repository successor context

`runtime.repository_successor_context.prepare_repository_successor_context` creates an independently admitted local planning revision after a committed repository change. It preserves the original instruction, native IntentIR document, every goal and task body, dependency relationships, and historical evidence. A deterministic identity mapping separates the successor's native tasks from the original tasks. Even when every finite requirement now matches, the successor retains the full task population and does not dispatch or omit tasks automatically.

The caller supplies the authenticated historical behavioral admission, its digest and task/owner/profile identities; existing native discovery, checked-cache and Intent owners; and a private state directory outside the repository. The source and Intent databases must remain separate, and their existing files must be owner-controlled (no group/world write permissions). The return contains the signed context, independent admission, materialization receipt, source head and semantic-manifest CID. This API does not start a daemon or grant completion authority.

The supported profile is the existing bounded Python integer-offset function, with explicit finite input domains and exact native Python/Lean tool identities. The successor conservatively rechecks **every** cache reverse reference to the predecessor snapshot, up to 64; overflow or an obligation outside that function/tool profile refuses preparation. Different offsets and finite domains remain separate obligations. Historical records are retained, while successor lookup uses the new full identity. Positive and refuted replacements both require fresh native observations.

Preparation reconstructs the semantic manifest and original Intent match on the successor, then repeats capture, proof checking and matching in independent cold DuckDB/CAS/cache owners. It compares source, domains, observations, compiled model/table and tool identities, active finite facts, residuals, and semantic inventories. Independently issued execution/artifact identifiers do not become semantic equality claims. These checks prove no general Python equivalence or unbounded whole-program property.

## Interrupted preparation

The state directory is owner-private and exclusively locked. An immutable, bounded request journal binds the historical artifact, predecessor head, new Git commit and tracked source bytes, owner identities, complete affected-record population, and producer bytes. The journal locates retries; it is not proof authority.

A retry resolves the exact durable source-publication operation and requires it to name the current head. Another successor, changed source, changed producers, changed affected population, or changed owner roots refuses replay. Each attempt has new observation output and independent cold owners, reruns native checks, and retains previous attempt artifacts. At most 16 attempts are admitted per journal. Cooperative cancellation and the native host scheduler remain active.

If the native task transaction committed but its reply was lost, retry accepts only the complete unchanged ready population with exact signed contracts, native identities, goals, dependencies, outputs, validations and acceptance requirements. It does not increment task revisions or overwrite tasks. A task already claimed or otherwise revised refuses this preparation replay. Profile initialization and manifest/admission verification use the existing native owners.

Source-head publication, proof checks, native task materialization and filesystem artifact publication are separate operations. Recovery uses their explicit identities and fences; it does not claim a cross-database/filesystem transaction. Historical contexts remain inspectable, while the original behavioral dispatch gate refuses the successor source. Production dispatch of a successor still requires its independent native lifecycle and current evidence fences.
