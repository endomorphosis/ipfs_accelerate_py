The worker campaign took 439.68 seconds including fresh setup and verification. Exactly two setup training epochs were requested: one root epoch and one child epoch over the changed source generation. Receiving and worker phases attempted no fitting or forward inference. These observations establish correctness and lifecycle behavior for this fixture; they do not establish a throughput improvement.

The native task bodies were 235,764 and 235,902 bytes, within the unchanged 262,144-byte Intent repository cap. The public instruction artifact was 574,567 bytes, within its separate existing public-artifact limit. All original dependency, validation, acceptance and permitted-output requirements survived installation. The native worker ran as UID1001, denied access to three observable owner-private roots, performed its authored edit, and completed through actual owner validation. The published change was restricted to `calc.py`.

The worker publishes a Git merge in the fixture. This campaign does not publish a new datasets source generation or establish a semantic reproof join after that edit. Cancellation during an arbitrary task is also outside the observed cancellation scope.

The new `preview_successor_native_profile.py` helper constructs the typed preview from independently authored, persisted planning records and current structural source observations. Every observer rereads its original policy/catalog/configuration/task-source records and actual checker/script bytes. Checker identity is observed here; no checker pass outcome or formal proof is injected into the preview. Later receiving operations have their own fresh bounded observations after the initial preview lease has closed.

The genuine run exposed a missing completion-retirement registration. `OwnerLocalCompletionService.close` now accepts the exact preview successor execution profile alongside the existing inventory profile, while preserving native runtime/scope custody, successful STOP, isolated UID cleanup and exact-handler checks. Six new regression cases exercise successful inventory/preview retirement, changed scope custody and unsupported profile rejection.

The fresh Docker harness also requires successful evidence copies before qualification, verifies the scheduler's selected source, and uses three independently observable private roots. The rebuilt offline image explicitly populates and loads the pinned native DuckDB extension cache. An unsupported legacy-builder heredoc had previously left that cache empty.

The [source4096 adapter](../../../ipfs_datasets/ipfs_datasets_py/logic/formalization/autoencoder/source_embeddings_4096_verified.py) consumes a completed native owner capability; it starts no encoder, service or resource job. It retains the exact source rows, full tokens, producer/model/library pins, CPU geometry and native release evidence. The handle is reusable only in its original process and native thread. Its ordinary diagnostic receipt grants no current registry/model/head, training, scan, execution, completion, publication or proof authority.

The one-row Leanstral operation took 104.01 seconds: 94.17 seconds verified the complete 67,135,119,264-byte model, and the native child took 9.84 seconds. This identifies full-model verification as the dominant cost in this particular operation. Batching can amortize one verified owner operation across multiple rows. Reusing verification across operations needs a separately authenticated immutable-model or incremental verification policy; a file-stat cache alone does not establish integrity.

There were 291 sampled RSS observations, with a maximum combined owner/child RSS of 562,708,480 bytes. This is sampled process RSS, not total cgroup memory. The dedicated cgroup retained its 8 GiB memory limit, zero swap, one CPU quota and PID limit. The child was reaped with no live group members, the own lease was absent after release, and the existing Leanstral service remained stopped before and after the operation. One row does not establish a smaller safe memory envelope.
