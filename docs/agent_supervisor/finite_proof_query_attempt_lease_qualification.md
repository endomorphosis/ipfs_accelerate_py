The change supplies the missing independent native attempt-lease check in the opt-in finite proof-query supervisor dispatch path. A current signed claim projection, runtime run lease and allocated worktree lease do not establish that the daemon's separate claim/attempt coordinator still admits the same attempt. The owner must check that actual native coordinator before permitting either an owner wrapper birth or an isolated coding-worker birth, and hold its authority until the birth acknowledgement closes.

## What the implementation checks

`DatabaseCoordinator.execute_with_task_claim_fence(claim, callback, *, minimum_remaining_ms=0)` validates the exact eight-field identity `task_cid`, `claim_id`, `attempt_id`, `attempt_number`, `lease_id`, `owner_session_id`, `fencing_token` and `fence_epoch`. It joins the actual `task_claims`, `fenced_leases` and `task_attempts` rows, their owner/task/attempt/fence identities, accepted claim/lease states, equal native expiry projections, a running attempt, the latest native token/epoch history and absence of a logical completion.

The checks run before the callback and again afterward in one real SQL write transaction. Before callback entry, the actual native expiry must satisfy `expires_at_ms > current_clock_ms + minimum_remaining_ms`; equality refuses. Afterward, the same tuple must remain live and the coordinator clock must not have moved backward. The post-check requires live authority; it does not impose a second full entry budget after the acknowledged callback. A successful result is returned only after the native transaction commits.

The callback receives the exact protected immutable `FencedLease` read inside that transaction. Its deadline comes from current native rows, rather than the caller's earlier claim projection. This matters for authentic renewal: the same lease/fence can be extended or shortened. A previous longer expiry cannot supply a later acknowledgement budget after a shorter renewal has landed.

The direct coordinator keeps its reentrant owner lock and its exclusive DuckDB connection while the callback runs. `ProcessSerializedDatabaseCoordinator` adds a common outer file lock, opens the native coordinator for the complete operation, and closes it before releasing that outer lock. Both the outer serialization lock and the connection's inner native database lock remain held through the callback. Supported coordinator operations from another adapter/thread/process wait; callback reentry into the same native coordinator or a serialized alias is rejected. Suppressing that exception does not make the enclosing callback guard succeed.

This transaction does not cover an external callback's store or an OS process birth. If the callback writes an external marker, starts a child, raises after an effect, reaches native expiry or fails the final native check/commit, the coordinator can roll back its own rows/events only. The caller must retain possible effects and cleanup duty. A raised guard is not evidence that the callback was never entered, that no external effect occurred, or that an already committed provider invocation can be rewritten as FAILED/completed/no effect.

## How the supervisor selects and holds the authority

The owner derives the daemon's actual coordination sidecar from the registered canonical native control database and the existing daemon sidecar producer. A worker request cannot supply an alternative coordinator path. The owner checks the exact bootstrapped daemon's kernel identity, process birth and registered CLI options, rejects sidecar overrides, and binds the existing canonical owner-controlled sidecar's device/inode/UID/link-count/mode identity. The sidecar must be distinct from the runtime coordinator which owns the run lease.

The owner opens that existing sidecar through the process-serialized coordinator with `require_existing_authority=True`. This mode rejects a missing, redirected, malformed or incomplete authority. It validates the landed columns, required indexes and coordinator interface/schema metadata without installing tables, repairing indexes or rewriting schema identity. The primitive requires an existing canonical regular file and stable identity across open; the broker applies the additional private-owner-directory, UID, single-link and mode requirements. Ordinary coordinator construction retains its existing installation behavior unless this explicit mode is selected.

For the finite route, the daemon selects the same process-serialized adapter even when its native task shard count is one. Selection requires complete typed owner routing, a live owner binding and an existing canonical owner-private dispatch socket. Those routing fields select transport; they do not grant task, proof, completion or process authority. Default unconfigured single-lane daemon routing remains unchanged.

The broker takes the native coordinator guard before its closing owner/server/proof work, using the reviewed coordinator-before-server lock order. It repeats the typed current claim, full task population, active grant, worktree, runtime run lease and final source/proof/index checks inside the callback. Immediately before sending `prepared`, it checks the actual guarded attempt lease has strictly more than the full 5,000 ms child acknowledgement budget. It then holds the native transaction and both process locks while observing the actual kernel birth acknowledgement and performs the coordinator post-check before releasing the handoff. The daemon's subsequent `on_started` action runs after those locks are released.

The two boundaries are `native_daemon_to_owner_wrapper` and `isolated_worker`. A broker observation saying `independent_live_attempt_lease_checked=True` applies only after a successfully closed guard at that boundary. A close receipt claims both boundaries only when the complete successful boundary history is present. A refused or unexecuted second boundary must not inherit the first boundary's result.

These remain distinct checks:

| Authority | Evidence it supplies |
| --- | --- |
| Typed native task/claim projection and active grant | Current selected task, revision, owner scope and permitted handoff |
| Daemon attempt coordination sidecar | Exact live claim/lease/attempt/latest-fence tuple held through acknowledgement |
| Runtime coordinator run lease | Owner's live supervisor-run reservation |
| Native worktree lease | Current allocated repository worktree reservation |
| Source/proof/index custody | Current selected code/evidence and applicability at the final dispatch gate |
| Actual kernel acknowledgement | The observed wrapper or isolated coding-worker process birth |

No single row, signature, grant, lease or metadata descriptor substitutes for all six.
