# Ranked capsule successor and benchmark qualification — 2026-10-12

The full supervisor can now select verified retrieval ranking through the
benchmark CLI and retain that selection when published source changes require a
new task context. This extends the earlier
[token-efficiency implementation](../terminal-token-efficiency-20261012/README.md),
whose dated measurements and operational limits remain historical evidence.
No new official Terminal Bench reward or provider-token reduction has been
established by the checks reported here.

## Select and retain the treatment

Use `--capsule-selection verified-retrieval-symbol-rank@1` when preparing a
`full` benchmark run, together with an explicit public `--task-profile` and a
new runtime archive containing the current ranking producers. The default is
`lexical-query-symbol-name@1`. Default configuration fields, arguments and
receipt shapes remain unchanged.

The option is frozen into benchmark controls and forwarded through Harbor and
the container driver to initial context preparation. Initial and admitted
context results must retain the requested selection. Collection exposes
selection drift, and execution refuses changed configuration. Opt-in archive
checks require exact current bodies for 24 producer modules, including the
source partition and pinned retrieval rebuild owners.

Previously prepared experimental ranked contexts must be rebuilt: cold load now
requires the selection declaration in both the initial descriptor and result,
matching the verified semantic projection. Default lexical records retain
their existing format.

The ranked treatment requires an independently signed program/support
partition from the public task profile. An unpartitioned legacy profile refuses
before indexing or planning; the ordinary lexical profile remains available.
The no-index arm rejects the option before input reads. An empty program
population cannot supply a ranked symbol selection. These boundaries preserve
the existing Doctor's signed source scope.

## Refresh ranking after source publication

Before a ranked successor is prepared, the owner historically replays the
predecessor's retained sources, AST snapshot and exact query result. It then
verifies current retrieval. Unchanged source scope reuses the original verified
selection; changed scope must use the pinned native retrieval rebuild policy.
Fresh retrieval is available before semantic capsules are compiled.

Unavailable or stale retrieval refuses the ranked successor before semantic
preparation. Owner state is checked around refresh. The new context preserves
the selected query, selector, unranked policy and capsule count/byte bounds.
Cold reload independently checks the selected retrieval binding and old-to-new
index/configuration lineage. Historical replay does not make an old source
current, and ranking does not authorize proof, execution, completion or omission
of a required fact. The default lexical refresh order is retained.
Existing producer limits still apply: the fixed lexical rebuilder refuses a
changed vocabulary; a learned rebuilder requires its separately pinned model
policy and assets.

## Current measurements

A separate instruction-deduplication census used the actual public
`largest-eigenval` instruction and source files with an **authored
administrative plan**. Its complete rendered coding input measured **57,423 to
56,452 bytes**, a reduction of **971 bytes (1.69%)**. Exact original restoration
was verified; there were zero real planning and coding provider calls. The
local source receipt is
`artifacts/supervisor-ranked-successor-20261012/pilot-preparation/public-census-02/qualification.json`.

This is input-byte evidence for `common-bindings-instruction@1`, not a measured
effect of ranked capsules. It includes the complete admitted public instruction
and does not count hidden provider scaffolding. No provider-token saving, task
completion or official verifier reward follows from the authored census.

The [first live attempt](live-census-01/blocked-census-summary-01.json) qualified
ordinary deployment, then failed its provider-free worker preflight: the
UV-managed CPython 3.12.12 runtime lacks `os.memfd_create`, both creation flags
and all six `fcntl` seal constants. Planning, Source384 inference and coding
never started. Native usage remains unavailable; no complete token ledger is
fabricated from the absence of dispatch. The owned container was stopped and
independently observed absent twice.

The [second live attempt](live-census-02/actual-live-census-02.json) passed
worker preflight, completed fresh Source384 inference in **10.02 seconds** and
completed one planning call through `llm_router`: **23,832 input + 1,353 output
= 25,185 native tokens**. The 207 reasoning tokens are already included in
output, and cached input was zero. Planning took 67.15 seconds; the complete
attempt including setup and cleanup took 716.61 seconds. The strict census
JSON parser then failed, so complete rendered input size remains unknown.
An isolated reproduction confirmed that logic-tree diagnostics can contaminate
strict JSON output. The private failing worker stream was not exported, so its
exact call stack is not retained. No coding call or official verifier ran. Both owned containers
were removed; the [retained accounting](live-census-02/closed-attempt-accounting-01-02.json)
includes both attempts (1,156.60 seconds). Dollar cost and complete benchmark
tokens remain unknown. The selected profile used Codex CLI 0.160.0 with
GPT-6.1 Sol/high, lexical capsules and Intent autoencoding disabled; it does not
measure a Grok route or an Intent-autoencoder treatment.

The [corrected third live census](live-census-03/actual-live-census-03.json)
completed successfully. Complete coding input measured **65,222 to 64,254 bytes**:
**968 bytes (1.484%)** smaller, with native exact restoration checked and the
instruction treatment selected. Byte-derived proxies were 16,306 to 16,064;
these are not measured provider tokens. Source384 inference completed in
13.81 seconds, nested within 18.46 seconds of initial context preparation.
Planning used **23,824 input + 1,491 output = 25,315 native tokens**, including
116 reasoning tokens already within output. There were zero coding calls and
no official verifier or reward. The owned container was removed and observed
absent twice; the frozen source and archive stayed unchanged.

The third attempt took 683.07 seconds end to end: deployment qualification took
493.77 seconds and the supervisor driver took 93.26 seconds. These are nested
phase observations, not a complete additive time breakdown. Across all three
retained attempts, [accounting](live-census-03/closed-attempt-accounting-01-02-03.json)
records **1,839.67 seconds** and **50,500 known native planning tokens** in two
observed sessions. First-attempt native usage stays null. Cost, complete
benchmark tokens and tokens per official verifier pass remain unavailable.
This fresh live result is separate from the authored-plan census above and
still measures only input representation, with lexical selection and Intent
autoencoding disabled. The [bounded review](live-census-03/closed-census-review-03.json)
checks receipt identities and arithmetic; it did not independently reconstruct
private prompt bodies. No full per-section prompt breakdown is available.
