# Real report-contract packet generator proposal

This source-only proposal prepares an unaccepted byte plan for the real LIR-9001 source reconciliation report. It has no materializer, dispatch CLI, board writer, task-state writer or accepting CLI. The author ran no generator, tests, product imports, provider calls, Git commands or native operations. Actual full Docker/native qualification remains pending: the latest root-reported r03 attempt stopped on the legitimate native CPU-stall guard. Nothing in this proposal fills a positive qualification observation.

`prepare_real_packet` requires an actual same-process `ParentedPhaseResourceReservation` in the ORCHESTRATION lane and explicit root-pinned observations. It checks the genuine owner independently of JSON evidence. The trusted root supplies three exact owned-runtime evidence pins: the actual complete V04 Docker terminal, successful retry-preservation publication receipt, and a root-observed two-consumed-attempt history binding. It also supplies an existing hashed public root-observation file and protected helper/native-source hashes. Missing, failed or incomplete qualification is refused before any packet bytes are returned. Serialized observations are engineering prerequisites, never native or acceptance capabilities; the root remains responsible for their actual provenance and finalized native owner/cleanup joins. Unit control documents are never supplied to this public entry.

The retry receipt uses the actual publisher schema `legal-ir-attempt-preservation-publication@1`, including its exact four deployed source hashes, actual published commit and51 passing policy/source controls. The generator independently reads those current source files and checks the deployment commit is an ancestor of the actual clean owned accelerator HEAD. The setting remains off in that deployment receipt; only the proposed new scheduler configuration selects `preserve_task_attempts:true` with a total cap of3. This is one remaining consumed ordinal after the two actual historical attempts, not three new attempts. The recovery publisher preserves this receipt schema and these joins without rerunning qualification.

The root-observed attempt-history input is a proposed explicit metadata envelope, not a generated observation. Its exact fields are `schema="legal-ir-root-observed-attempt-history@1"`, `task_id`, `canonical_task_cid`, `consumed_attempts=2`, `board_namespace`, `orchestration_namespace`, `runtime_paths`, `source_observation_pin` (`absolute_path`, `bytes`, `sha256`) and `history_reset_performed=false`. The task's identity/provenance `board_namespace` comes from the actual public task parser; the separate `orchestration_namespace` comes from scheduler configuration. Both must match their independently observed sources. The referenced source is actual public redacted host history metadata under the owned test-log root. The generator verifies its pin and compares the supplied canonical CID/state lineage with identities independently derived by the real public daemon parser and `canonical_task_identity`. It does not read a database, create that observation, reset state, or treat namespace changes as history resets. A fresh actual history recheck is required before any separate dispatch authorization.
