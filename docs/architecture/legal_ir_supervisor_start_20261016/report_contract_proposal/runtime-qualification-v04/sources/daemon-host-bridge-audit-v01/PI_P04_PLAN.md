# PI-P04: same-process daemon host integration

The current ordinary daemon cannot pass genuine native owners and its original local database connection into the callable H3 callback/freezer. This bundle is a source audit and a bounded implementation plan. It contains no executable patch, operational enablement, tests run by the author, provider outcome or completion authority. Frozen generations and actual runs remain unchanged.

`TASKS.json` contains one goal, six subgoals and eighteen dependency-ordered tasks for a future reviewed agent-supervisor work queue. It is planning data, not an enqueued task or a grant. `EVIDENCE.json` records exact actual source hashes and line proofs. API names described as proposed do not already exist.

## Existing source and missing connections

The generic launcher holds its actual native root, phase and parented owner in its own interpreter, then starts a child through `Popen`; that child receives environment values, not those objects (E01–E02). `PortalImplementationDaemon` and its configured `run_once()` loop have no native ancestor or retained connection parameter (E03–E06). Both ordinary provider seams use the external process runner. Lease IDs, JSON receipts and environment variables cannot establish H3's same-process ownership.

The existing public `ParentedPhaseResourceReservation(..., parent_lease=actual_lease, ...)` requires an exact native `ResourceLease` beneath a root and the current owner PID (E07). `RepositoryPhaseLease.native_options()` and `PipelinePhase.native_options()` really return actual parent objects (E09/E11), but neither is wired into this daemon. `RepositoryResourceBridge.reserve()` creates a top-level ORCHESTRATION root, so inserting it behind current host admission would duplicate admission (E10). Its typed budgets also require CPU slots at least equal to process slots, making the required 3 CPU / 16 slot profile incompatible without a policy change (E08). The integration should use actual native SDK objects directly, preserving the existing profile.

`PortalTaskState.save/load` delegate to the state-control-plane producer (E12). Its `_connect` opens a fresh wrapper and executes DDL, and each board/lane save/load closes its wrapper in `finally` (E13–E14). No retained connection accessor is present. A local `DuckDBConnection` holds an exclusive flock for its lifetime; every local open creates a new wrapper and flock handle (E15–E17). Retaining a separate connection while unchanged state I/O reopens the same file can therefore collide with the held lock. This is a source-derived failure path, not an executed deadlock result.

Fixing only launch-boundary capture would be insufficient: progress callbacks reload and save state while the provider runs (E18), and selection, preflight, cancellation and terminal paths also use state producers. `DatabaseImplementationDaemon` has a retained private execution-sidecar connection, but that separate interface and target do not supply the original Portal control-plane connection (E19–E20). The host must not guess an accessor or substitute the sidecar.

## Bounded patch scopes

**Borrowed state I/O, tasks 03–05.** Add an explicit nonowning scope in `portal_task_state_control_plane.py` for one actual, already-open local `DuckDBConnection` and exact resolved state target. Bind original object identity, current PID and approved owner thread. Under the actual execution condition, reject closed, poisoned, retired, transactional, remote or catalog-switched handles. Do not reconnect, pool, wrap a new handle, use a serialized representation or run schema/migration work. A small owned-or-borrowed context should preserve the four original state SQL paths: default behavior retains its existing open/DDL/close; the opt-in path uses the borrowed handle and never closes it.

The scope must cover the whole active attempt, including `run_once` selection and preflight. Audit every producer that can resolve to the same target, including plan/task-source operations. Unknown same-target reopen must refuse before dispatch. Off-thread access must refuse or use a separately reviewed exact object path, and must never fall back to another local open. Initial connection acquisition and eventual close belong to the trusted host producer. The freezer remains SELECT-only and continues to reject invalid connections (E22). No global connection pool, connection-ownership transplant or ambient monkeypatch is proposed.

**Native host entry, tasks 02/06–07.** Add a direct single-process opt-in entry receiving an already-admitted actual phase and existing local connection. Review its new public signature and object-lifetime contract before implementation. It must not accept caller-chosen task, baseline or attempt ordinal. Run the original daemon inside the original host frames and pass actual objects through a scoped internal session. Current CLI/default `run_once` paths remain unchanged. The external generic-parent topology cannot deliver these objects and must not silently create another root in its child.

Preserve root/phase at 3 CPU / 4096 MiB / 16 child slots. Admit distinct original sibling owners: provider 1 CPU / 1024 MiB / 8 slots, watchdog 1 CPU / 512 MiB / 4 slots, and fresh freezer 1 CPU / at least 512 MiB / 4 slots. Use the actual held SDK and original scheduler/policy. Prebind actual provider/watchdog consumers through C before effects, precharge exact disjoint private/output/external storage, and preserve finite deadlines at most 3600 seconds. Freezer ownership cannot reuse provider child history. Admission and storage must be measured and refused within current caps, not inferred from this plan.

**Original board and dispatch capture, tasks 08–11.** Frozen freezer V02 requires `daemon.todo_path` inside the actual invocation workspace plus an actual active lifecycle (E21). Actual `todo_path` remains the original configured/task-source path, while an ephemeral workspace is chosen later (E23–E25). Direct repo mode does not supply that ephemeral lifecycle. This mismatch requires a bounded additive freezer V03 capture-layout successor; assigning `daemon.todo_path` to the worktree or weakening the guard is not a solution.

Derive the authoritative board's relative path only from the actual canonical daemon repository and its original retained board path. Verify the active worktree lifecycle belongs to that repository. Independently derive its workspace board copy; retain both authoritative original bytes and the exact workspace baseline board blob. Check both SHA-bound copies throughout capture and freezing. Task parsing, canonical CID/key and frontier remain bound to the original authoritative board. Callback callers cannot choose another board, repository association or baseline. Refuse before attempt consumption if the original board is outside the supported repository layout.

Before consuming ordinal 3, preflight actual worktree, Git/common roots, storage bounds, skipped/hidden index flags, tracked modes, submodules, symlinks and hardlinks (E34/E37). The report-only profile does not admit arbitrary full repository layouts. Unsupported layouts remain blockers; do not enlarge caps or silently relax frozen guards. Preserve manual completion, all original 64 task identities/frontier, the report path and peer counters.

At the existing provider seam, retain original selected task/state objects and the locally discovered full baseline. Construct one immutable G invocation from the original prompt/workspace and explicit environment/temp/private borrowed sinks. The original `_mark_implementation_started` alone consumes ID/CID counters from 2 to 3, with cap 3 (E38). After the original launch-boundary state save, pass the identical invocation, baseline and existing connection to original capture. Keep the enforcing decision-runtime boundary, then call H3 with genuine owners and C hold. A source-pinned plain callback invokes the public freezer only while H3 authenticates its actual success outcome and exact invocation identity (E29/E36).

The callback returns inert candidate metadata. Add an explicit candidate-pending-native-validation result before generic validation/commit/merge/completion. An integer provider return code cannot replace native acceptance. Actual candidate observation, native validation/controller integration and canonical completion remain separate gates.

## Custody must stop normal settlement

Tasks 12–14 must precede operational integration. `OrdinaryCustodyPending` is an `Exception`; the current repo handler would mark implementation finished and save an outcome, then its unconditional `finally` releases implementation lock and resource/task claims (E26). The ephemeral handler can clean the worktree and continue into state/lifecycle finalization (E27–E28). Re-raising through those finalizers is insufficient.

Add an explicit typed pending branch before generic handlers and gate affected outer finalizers. Retain the actual pending exception and original host/native frames, owners, consumers, lifecycle, invocation, task/state, baseline, connection and claim metadata. Unknown cleanup cannot clear active state, restore counters, mark finished, publish terminal success/failure, clean worktree or release claims. Keep the dispatcher stopped inside the original custody scope. Observe only: no provider retry, blind reclose, new grant, deadline reset or interpretation of renewal as restored productive authority.

Provider and freezer cleanup are separate. Frozen V02's `_Git.run` has a real local `Popen`; failed wait/group proof raises ordinary refusal (E35). The host must retain the actual freezer owner and original process/reference graph on that uncertain branch even if provider/watchdog are stopped. A bounded typed holder in the freezer successor may be needed. No PID reconstructed from metadata supplies cleanup permission.

Only independently observed same-daemon/runtime/CID/name/kernel/private-path and original native-group closure permits provider consumer acknowledgement. Prove freezer group stopped independently too. Release original public consumers, forget only after actual row drain, persist durable bounded output, then use public stopped owner release if ancestry was revoked. Preserve ordinal 3, claims and lifecycle until proof permits original-producer settlement. Retained same-process capacity does not guarantee custody after host death (E39); this plan makes no such claim.

## Qualification and publication

Tasks 15–18 separate source controls, genuine nonmodel components and live integration. Controls cover owned/borrowed SQL and close order, wrong target/thread/poison/transaction refusal, original dual-board identity, pending-custody finalizer order and distinct freezer cleanup. Positive controls cannot fabricate actual owners, callbacks or connections.

A fresh genuine native fixture should use an actual existing private fixture database and same-process owners, exercise all state I/O on the original connection, prove no second lock/open and retain caller usability. Deliberately abort H before dispatch with original exception identity and consumer drain. Separate physical nonmodel cases should test actual caller cleanup and cancellation retention. These qualification jobs change no production task counters or canonical state and make no provider calls. Source projections and AST controls do not establish runtime authority.

Publish exact immutable source/request/root/result joins and preserve failed runs. Actual provider callback/freezer positive qualification, genuine candidate observation, native checker/controller acceptance, requested Codex backup routing, legal fidelity, decoder accuracy and `lake build legal` remain explicit prerequisites. Plan entries and publication do not enable dispatch.
